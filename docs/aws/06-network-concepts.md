# AWS 네트워크 개념 — VPC / 서브넷 / IGW / 라우팅 테이블

> 지금 Terraform으로 만들고 있는 것들이 각각 무엇이고 왜 필요한지.
> 코드를 쓰기 전에 이 그림이 머리에 있어야 한다.

---

## 0. 왜 네트워크부터 만들어야 하나

AWS는 전 세계 사람들이 **같은 물리 장비를 나눠 쓰는** 서비스다.
내 서버를 아무 데나 띄우면 남의 서버와 같은 네트워크에 섞인다. 그건 곤란하다.

그래서 AWS는 먼저 **"이건 내 구역"** 이라고 논리적으로 울타리를 치게 한다.
그게 **VPC** 이고, 그 안을 어떻게 구획하고 어디로 길을 낼지가 나머지 셋이다.

집을 짓기 전에 **땅을 사고, 구획을 나누고, 도로를 놓는 것**과 같다.
지금은 건물(앱, DB)을 올리기 전 단계다.

---

## 1. VPC — 내가 빌린 땅

**Virtual Private Cloud.** AWS 안에 만드는 나만의 격리된 네트워크.

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

- **리전 단위**로 존재한다. 서울에 만든 VPC는 도쿄에서 안 보인다
  (어제 콘솔에서 VPC가 안 보였던 이유가 이거다)
- 계정마다 리전별로 **기본 VPC**(`172.31.0.0/16`)가 이미 하나 있다. 우리는 따로 만든 것

### CIDR 표기법 — `10.0.0.0/16` 이 무슨 뜻인가

IP 주소는 `10.0.0.0` 처럼 네 덩어리, 각 덩어리가 8비트라 총 32비트다.
`/16` 은 **"앞의 16비트는 고정"** 이라는 뜻이다.

```
10  .  0  .  0  .  0   /16
└──┬──┘  └────┬────┘
 고정 16비트   자유 16비트  →  10.0.???.???
                            사용 가능 IP 약 65,536개
```

| 표기 | 고정 부분 | 쓸 수 있는 IP |
|---|---|---|
| `10.0.0.0/16` | `10.0.` | 약 65,536개 (VPC 전체) |
| `10.0.0.0/24` | `10.0.0.` | 256개 (서브넷 하나) |
| `10.0.1.0/24` | `10.0.1.` | 256개 (다른 서브넷) |

**숫자가 클수록 좁은 범위**다. `/16` 짜리 큰 땅을 `/24` 짜리 구획들로 쪼개는 것.

---

## 2. 서브넷 — 땅을 나눈 구획

VPC의 IP 범위를 쪼갠 것. **반드시 하나의 가용 영역(AZ)에 속한다.**

### 가용 영역(AZ)이 뭔가

한 리전 안에 있는 **물리적으로 떨어진 데이터센터**다.
서울 리전에는 `ap-northeast-2a`, `2b`, `2c`, `2d` 가 있다.

한 건물에 불이 나거나 정전이 나도 다른 건물은 살아있다.
그래서 **서비스를 최소 2개 AZ에 나눠 두는 것**이 기본이다.

```
    서울 리전 (ap-northeast-2)
┌──────────────────┬──────────────────┐
│   AZ: 2a         │   AZ: 2c         │
│  (데이터센터 A)   │  (데이터센터 C)   │
│                  │                  │
│  public-a        │  public-c        │
│  10.0.0.0/24     │  10.0.1.0/24     │
│                  │                  │
│  private-a       │  private-c       │
│  10.0.10.0/24    │  10.0.11.0/24    │
└──────────────────┴──────────────────┘
```

우리가 서브넷을 4개(2 AZ × 2종류) 만드는 이유:
1. **AZ 하나가 죽어도 서비스가 살아있게**
2. **ALB가 최소 2개 AZ의 서브넷을 요구한다** (나중에 만들 때 안 만들어 두면 막힌다)
3. **RDS 서브넷 그룹도 2개 AZ를 요구한다**

## 3. 인터넷 게이트웨이(IGW) — 단지 정문

VPC를 인터넷과 이어주는 출입구. **VPC당 하나만** 붙일 수 있다.

```hcl
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}
```

⚠️ **중요**: IGW를 붙였다고 해서 인터넷이 되는 게 아니다.
정문을 세워놨을 뿐, **거기로 가는 길(라우팅)** 을 알려줘야 한다.

---

## 4. 라우팅 테이블 — 이정표

**"이 목적지로 가려면 어디로 가라"** 는 규칙 목록.
서브넷마다 라우팅 테이블이 하나씩 붙는다.

퍼블릭 서브넷에 붙일 라우팅 테이블은 이렇게 생겼다:

| 목적지(Destination) | 대상(Target) | 뜻 |
|---|---|---|
| `10.0.0.0/16` | `local` | VPC 안끼리는 그냥 통한다 (자동 생성, 지울 수 없음) |
| `0.0.0.0/0` | `igw-xxxxx` | **그 외 전부**(=인터넷)는 정문으로 보내라 |

`0.0.0.0/0` 은 "모든 IP"라는 뜻이다. 가장 넓은 범위라 **제일 마지막에 적용되는 기본 규칙**처럼 동작한다.
더 구체적인 규칙(`10.0.0.0/16`)이 먼저 매칭되고, 아무 데도 안 걸리면 `0.0.0.0/0` 으로 간다.

```hcl
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
}
```

그리고 **어느 서브넷에 이 테이블을 붙일지** 따로 지정해야 한다:

```hcl
resource "aws_route_table_association" "public_a" {
  subnet_id      = aws_subnet.public_a.id
  route_table_id = aws_route_table.public.id
}
```

퍼블릭 서브넷이 2개니 이 연결도 2개 필요하다.

## 5. 퍼블릭 서브넷과 프라이빗 서브넷의 진짜 차이 ★

**면접 단골 질문이다.**

흔한 오해: "서브넷을 만들 때 퍼블릭/프라이빗을 고르는 거 아닌가?"
→ **아니다. 그런 설정은 없다.**

> **차이는 오직 하나: 연결된 라우팅 테이블에 `0.0.0.0/0 → IGW` 경로가 있느냐.**

- 있으면 → **퍼블릭 서브넷**
- 없으면 → **프라이빗 서브넷**

즉 서브넷 자체는 똑같고, **어떤 이정표를 붙였느냐**로 성격이 갈린다.
프라이빗 서브넷에 라우팅 테이블을 따로 안 만드는 이유도 이것이다 —
VPC 기본 라우팅 테이블에는 `local` 경로만 있어서 자연히 프라이빗이 된다.

> `map_public_ip_on_launch = true` 는 별개다. 이건 "이 서브넷에 뜨는 인스턴스에
> 공인 IP를 자동으로 붙여라"는 옵션이다. 공인 IP가 있어도 IGW 경로가 없으면 인터넷은 안 된다.

## 6. 이 프로젝트에서 뭐가 어디 들어가나

지금 만드는 땅 위에 나중에 이렇게 올린다.

```
                    인터넷
                      │
                 ┌────▼────┐
                 │   IGW   │
                 └────┬────┘
   ┌──────────────────┼──────────────────┐
   │  VPC 10.0.0.0/16 │                  │
   │                  │                  │
   │  ┌───────────────▼───────────────┐  │
   │  │  퍼블릭 서브넷 (2a, 2c)        │  │
   │  │   • ALB      ← 사용자 요청 받음 │  │
   │  │   • Fargate  ← Spring Boot 실행│  │
   │  └───────────────┬───────────────┘  │
   │                  │ 3306             │
   │  ┌───────────────▼───────────────┐  │
   │  │  프라이빗 서브넷 (2a, 2c)      │  │
   │  │   • RDS MySQL                 │  │
   │  │     인터넷에서 직접 접근 불가   │  │
   │  └───────────────────────────────┘  │
   └─────────────────────────────────────┘
```

**왜 DB를 프라이빗에 두나?**
DB는 인터넷에서 직접 접근할 이유가 없다. 앱 서버를 통해서만 오면 된다.
프라이빗에 두면 **애초에 인터넷에서 도달할 경로가 없어서** 공격 표면이 줄어든다.

---

## 7. NAT Gateway를 왜 안 만드나

프라이빗 서브넷에 있는 리소스가 **인터넷으로 나가야 할 때**(패키지 다운로드 등)
NAT Gateway가 필요하다. 들어오는 건 막고 나가는 것만 허용하는 장치다.

**우리는 안 만든다.**
- RDS는 인터넷으로 나갈 일이 없다
- NAT Gateway는 **월 4만원대** — 이 구성에서 제일 비싼 리소스
- Fargate는 퍼블릭 서브넷에 두고 보안그룹으로 보호한다

교과서적 구성은 아니지만, **왜 그렇게 했는지 설명할 수 있으면 그게 오히려 가산점**이다.

---

## 8. 라우팅 테이블 vs 보안그룹 (다음 단계 예고)

둘 다 "접근 제어" 같아 보여서 헷갈린다. 역할이 완전히 다르다.

| | 라우팅 테이블 | 보안그룹 |
|---|---|---|
| 역할 | **길** — 어디로 갈 수 있나 | **문지기** — 누가 들어올 수 있나 |
| 단위 | 서브넷 | 리소스(인스턴스, RDS 등) |
| 비유 | 도로와 이정표 | 건물 출입 카드 |

길이 있어도 문지기가 막으면 못 들어간다. 둘 다 통과해야 연결된다.

## 정리 — 오늘 만드는 8개

| # | 리소스 | 역할 |
|---|---|---|
| 1 | `aws_internet_gateway` × 1 | 인터넷 출입구 |
| 2~5 | `aws_subnet` × 4 | 2 AZ × (퍼블릭, 프라이빗) |
| 6 | `aws_route_table` × 1 | `0.0.0.0/0 → IGW` 이정표 |
| 7~8 | `aws_route_table_association` × 2 | 퍼블릭 서브넷 2개에 이정표 붙이기 |
